# H.264 video over MQTT

Goob now runs software x264 instead of delta JPEG, using the same Camera module,
View/Stop actions, input mappings, compact `o/video` topic, and demand leases.
The shared camera module still defaults to PBVD for existing installations.

## Select the codec

In `services.mqtt_bridge.media.video_publisher`:

```json
{
  "codec": "h264",
  "bitrate": 400000,
  "preset": "ultrafast",
  "keyframe_interval": 5,
  "publish_width": 640,
  "publish_height": 360,
  "publish_fps": 15
}
```

In that robot's `services.module_host.modules` camera instance, advertise the
same codec:

```json
{
  "id": "camera",
  "use": "modules/camera/module.json",
  "formats": {"stream": {"codec": "h264"}}
}
```

Restart the robot control service after changing these settings. To use delta
video again, set **both** codec values to `pbvd`. The Goob example includes H.264.
`--codec h264` / `--codec pbvd` overrides the publisher's configuration for manual
runs, but its advertised manifest must still match. Instances can use `formats`
to override codec/rate/channels on media endpoints without editing shared files.

Install PyAV on encoder and gateway: Debian system Python can use
`apt install python3-av`; a Python virtualenv can use `pip install 'av>=10,<19'`.
Goob uses Debian PyAV 10 with libx264; ARL's web virtualenv uses PyAV 18.1.
No hardware encoder or driver changes were made.

## Wire protocol and recovery

Each QoS 0, non-retained MQTT message contains one complete Annex B H.264 access
unit after a 40-byte network-order header, `!4sBBH16sIQHH`:

| Field | Value |
| --- | --- |
| magic | `PBVH` |
| version | 1 |
| flags | bit 0: IDR keyframe; other bits zero |
| reserved | zero |
| stream ID | 16 random UUID bytes, new for each encoder instance |
| sequence | 32-bit frame sequence, beginning at zero |
| timestamp | 64-bit wall-clock milliseconds before resize/encoding |
| width, height | 16-bit dimensions each |

The encoder uses baseline H.264, no B frames, one encoding thread, and
`zerolatency`. Every IDR repeats SPS/PPS. With Goob's GOP of 5 at 15 fps, there is
an independent restart point about every 333 ms. Messages are limited to 2 MiB;
encoded dimensions must be even and between 16×16 and 1920×1080.

The gateway rejects invalid framing and duplicate/old sequences. A changed
stream ID, changed dimensions, missing sequence, or decoder failure invalidates
the decoder reference state. Dependent frames are dropped until a self-contained
IDR arrives. The publisher starts a new encoder/stream ID on source or broker
reconnection and after failed publishing. It holds at most one unpublished
application message and drops input frames before encoding while it waits;
this does not bound TCP or broker buffers. There is no retained stale video.

Media dispatch remains isolated from the legacy JSON handler, including errors.
Gateway decoding uses a single thread with no delayed frame threading. The
existing HTTP camera endpoint serves the latest decoded JPEG. Thus **H.264 is
used on the robot → MQTT → gateway path**; the browser still receives JPEG,
including over plain HTTP. Browser-native H.264/WebCodecs is separate work.

The camera card reports the selected codec, observed frame rate, and MQTT
payload bandwidth. `GET /modules/api/media/camera/stream?robot=...&revision=...&stats=1`
returns activity, sequence, decoded frames, bandwidth, decoder resets, dropped
packets, and estimated source-to-gateway delay. Bandwidth includes the PBVH/PBVD
payload header; it excludes MQTT/TCP/IP/TLS overhead. Header timestamps require
reasonably synchronized clocks and are not camera-exposure-to-display latency.

## Live observations on Goob and ARL

Full data and JPEG samples are in
[the live results directory](../analysis/media-benchmark/results-2026-10-19-live/).
Both runs used the same physical camera scene, 640×360 output at 15 fps,
1280×720 shared capture, GOP 5, and the HTTP gateway frame endpoint. Warmup was
excluded from the means; these are sequential observations, not synchronized
same-frame quality comparisons.

| Measurement | PBVD Q8 | H.264 400 kbit/s |
| --- | ---: | ---: |
| MQTT payload bandwidth | 555.5 kbit/s | 408.1 kbit/s |
| Received frame rate | 15.0 fps | 15.0 fps |
| Publisher CPU, % of one core | 63.8% | 35.2% |
| Shared capture CPU, % of one core | 43.6% | 44.5% |
| Combined camera processes, % of one core | 107.4% | 79.7% |
| Offline observations | 0 | 0 |

H.264 reduced publisher CPU about 45% and MQTT payload bandwidth about 27%.
Shared capture still accounts for substantial CPU. Both main observations ran
35 seconds, and H.264 decoded continuously without missing packets or unexpected
decoder resets (its initial decoder creation counts as one reset).

The initial PBVD timestamp was written after encoding. It was corrected to the
same pre-encoding boundary as H.264, then PBVD was observed for another 25s:
mean source-to-gateway delay was 23.0 ms versus H.264's 24.6 ms. Treat this small
difference as approximate: the measurements depend on clock synchronization and
exclude camera acquisition and browser polling/rendering. The browser's display
transport is unchanged. Existing controlled same-frame quality comparisons are
in the [original benchmark](../analysis/media-benchmark/START-HERE.md).

Reproduce a live observation on ARL:

```sh
python3 /path/to/Pebble/analysis/media-benchmark/live.py \
  --url http://127.0.0.1:8080 --robot pebble/robots/goob \
  --seconds 35 --output /tmp/live-video.json
```

This temporarily requests camera publishing, renews only its own lease, saves a
JPEG sample and JSON observations, and releases its request afterward. It sends
no drive commands. No automated test suites or packet-loss/broker-interruption
injection were run for this change; those recovery paths were reviewed in code.

## Talk audio upload correction

The browser previously discarded every new 40 ms PCM chunk while an HTTP upload
was in flight. Round trips longer than a chunk could remove whole stretches of
speech, causing discontinuities before Opus encoding. Talk now queues and
coalesces waiting chunks in order, with one upload in flight. Waiting audio is
bounded to 240 ms; excess stale chunks are discarded with a congestion notice.
Stopping Talk now flushes queued speech and allows in-flight uploads to finish
before the stop request is sent, avoiding a truncated final syllable. Goob's
speaker queue is bounded to 16 × 20 ms frames to accommodate these batches.
Listen's audio path and codec settings were left as they were. The queue change
addresses an observed code defect; subjective speaker quality still needs
confirmation after a page refresh.
